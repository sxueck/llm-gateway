# PRD：运维监控（整合性能监测）

- **状态**：需求已确认，待技术设计与实施；本文不是已上线功能说明
- **版本**：1.0
- **目标用户**：网关管理员
- **范围**：监控中心「运维监控」、请求日志钻取、首页统计口径一致性及必要的数据留存调整

## 1. 产品结论

把监控中心现有的「性能监测」升级为「运维监控」，而不是再建一套重复看板。新页面统一查看虚拟密钥用量、实际模型与供应商的成功率及性能，并允许逐层筛选、钻取到请求日志。流量分析和 Worker 监控保留独立入口；首页继续显示全局概览，但须与运维监控使用相同的统计时间和指标定义。

首版以**请求日志口径**衡量成功率，不声称能够量化每次上游重试的成功率；以人工观察和排障为目标，不做告警或通知。

## 2. 背景与现状

- `packages/web/src/layouts/MainLayout.vue`：监控中心目前包含 Worker 监控、性能监测、流量分析；`PerformanceMonitoringView.vue` 固定展示近 7 天的供应商 × 模型用量、成功率、TFFB、输出速度和 Tokens。
- `packages/backend/src/routes/config.ts` 的 `/performance-metrics` 固定近 7 天；`packages/backend/src/db/repositories/api-request.repository.ts` 的 `getPerformanceMetrics` 按 `provider_id + model` 统计，不提供虚拟密钥视角。
- 首页 `/stats` 提供 `24h / 7d / 30d / all`；当前 `24h` 是滚动时间，而 `7d / 30d` 从上海时区自然日零点算起。运维页若独立实现滚动窗口，会与首页出现相同标签、不同数字。
- 请求明细 `api_requests` 有密钥、供应商、模型、状态、Tokens、TFFB 和响应时间；默认明细保留 14 天。清理任务在启动时及随后每 24 小时执行，先汇总再删明细。`api_request_daily_summaries` 按上海自然日、密钥、供应商、模型保存请求数、成功数、Tokens 和部分耗时总和，但没有可还原完整长期 TFFB、输出速度的字段。
- 请求日志接口已支持时间、密钥、供应商、模型、状态过滤；页面当前只提供时间、密钥、状态控件。
- `disable_logging` 目前使代理不传请求/响应正文给日志写入路径，但仍可能写入单条元数据（包括错误信息、IP 等）；统计及日志读取又将此类密钥排除。这与本 PRD 确认的隐私和统计需求不一致。

## 3. 已确认的决策

| 议题 | 决策 |
| --- | --- |
| 页面关系 | 性能监测合并升级为运维监控；流量分析、Worker 监控保留独立入口 |
| 视角 | 总览、虚拟密钥、实际模型、供应商 |
| 成功率 | 沿用请求日志中的 `status = success`，不是上游尝试成功率 |
| 时间 | 默认最近 24h，切换最近 7d、最近 30d；滚动窗口，与首页保持一致；手动刷新并显示数据更新时间 |
| 精度 | 30d 需精确滚动，不接受按自然日近似；新数据需要小时级汇总和边界明细，首页同步修改 |
| 密钥呈现 | 仅管理员，显示名称、内部 ID 和掩码，不显示原始密钥 |
| 用量 | 请求数、成功/失败数、成功率、输入/输出/缓存 Tokens、最近使用时间；不含费用与配额 |
| 性能 | 长期按天保留可加权计算的均值指标；首版不要求 P95 |
| 禁用日志 | 不记录请求/响应正文；可统计密钥级用量和性能，可向管理员显示脱敏单条元数据，不显示敏感错误或 IP |
| 排障 | 筛选、排序、图表联动，携带条件钻取到请求日志；首版不做阈值告警与通知 |

## 4. 目标、非目标与成功标准

### 4.1 目标

1. 管理员在相同时间范围内看出哪个密钥用量最高、哪个模型/供应商成功率或响应性能较差。
2. 从总览 → 维度明细 → 请求日志完成排障；看不到单条明细时明确说明原因。
3. 首页和运维页对同一范围及同一统计集合展示一致的请求数、成功率与 Tokens。
4. 在明细清理后保留可用的日级长期性能均值；对于历史缺口不伪造精度。
5. 在允许统计 `disable_logging` 密钥的同时，确保不泄露请求/响应正文、敏感元数据或原始虚拟密钥。

### 4.2 非目标

- 上游每次重试/故障切换的尝试级成功率，或把日志成功率解释成供应商真实可用性；
- 自定义告警规则、推送通知、自动处置；
- 费用估算、配额余额、SLA 承诺与 P95/其他分位数；
- 将流量预测和 Worker 运行记录混入请求成功率；
- 对已经删除、未采集的请求及性能指标进行推测性回填。

### 4.3 验收成功标准

同一筛选范围内四个视角的数据可核对；首页和运维页的全局指标一致；禁用日志密钥可查看聚合及允许的脱敏元数据，却不能通过任何运维/日志接口取得请求正文、响应正文或敏感错误内容。

## 5. 用户场景

1. **用量排查**：管理员发现总 Tokens 上升 → 切换「虚拟密钥」按总 Tokens 排序 → 看输入、输出、缓存 Tokens 及最近使用时间 → 按密钥筛选趋势与模型分布 → 在可用明细期钻取单条请求。
2. **模型故障**：总览成功率下降 → 选择模型 → 查看该模型分供应商的请求数和成功率 → 选择失败供应商 → 带时间、模型、供应商及失败状态打开请求日志。
3. **供应商性能**：某供应商平均首字节耗时上升 → 查看其模型拆分及有效样本数 → 判断是特定模型还是普遍异常；性能值缺失时显示「—」，不得显示 0 ms。
4. **历史复盘**：切换 30d → 查看按天趋势及新采集的长期性能 → 对尚无完整小时/性能历史的区间看到覆盖提示，不把近似值冒充精确滚动结果。
5. **禁用日志的密钥**：仍计入用量和成功率；可查看无正文且已脱敏的单条元数据，不出现请求或响应文本。

## 6. 信息架构与页面需求

```text
监控中心
├─ 运维监控（由性能监测升级）
│  ├─ 总览
│  ├─ 虚拟密钥
│  ├─ 模型
│  └─ 供应商
├─ 流量分析（保持独立）
└─ Worker 监控（保持独立）
```

旧的性能监测入口应更新名称与指向；旧路由如存在书签需兼容跳转到新页面，不出现两个统计口径不同的性能页。首页仍为全局概览入口；需要沿用其已有图表能力，不复制另一份指标计算。

### 6.1 公共筛选与反馈

- 默认 `24h`；可切换 `7d / 30d`。每次加载返回并显示确切 `startTime`、`endTime`、时区及 `updatedAt`。`endTime` 在点击刷新或切换条件时固定，避免同一屏多请求因取样时刻不同而不一致。
- 维度筛选：虚拟密钥、实际模型、供应商，允许组合；「总览」卡片与趋势须使用同一组条件。不可用的筛选项显示为空而不是偷偷清除。
- 选择维度后保持时间范围；清除筛选有独立操作。表格提供按请求数、成功率、Tokens、平均耗时排序，后台分页；搜索密钥名与模型名。
- 请求数为零、筛选无结果、请求失败、部分历史不可用、指标缺样本、查询超时分别提供可辨认状态；刷新按钮显示加载中，不重复触发并发请求。
- 成功率对低样本数不加无依据的「异常」红标；表格同时显示成功/失败数及分母，供人工判断。

### 6.2 总览

- 指标卡：请求数、成功数、失败数、成功率、输入/输出/缓存 Tokens、平均 TFFB、平均响应时间、平均输出速度。
- 趋势：请求数与成功率（24h 可逐小时；7d、30d 按上海时区逐天展示）。滚动窗口首尾天是**部分日**，图表必须标注，柱/点仅统计与查询窗口相交的时间，不用整日值填充。
- 对比入口：按请求数或失败数排序的模型和供应商；点击后进入对应视角，沿用筛选条件。

### 6.3 虚拟密钥

- 列：名称、掩码、内部 ID（可复制）、请求数、成功数、失败数、成功率、输入/输出/缓存 Tokens、最近使用时间。名称重名时用 ID 区分。
- 支持选择密钥后查看该密钥的按天/小时趋势、模型与供应商拆分；禁用或删除的密钥如仍有历史汇总，保留历史归属和可辨认标识，不显示原始密钥值。
- 掩码沿用 `maskKey` 规则：长度不超过 8 的密钥全掩，其他最多末四位；不能因调用已有管理 API 而把包含完整 `keyValue` 的响应传给此页面。

### 6.4 模型与供应商

- 模型以日志记录的**实际模型**为唯一聚合名；模型视角提供按供应商拆分，供应商视角提供按模型拆分。
- 均展示请求数、成功/失败数、成功率、Tokens、平均 TFFB、平均响应时间、平均输出速度，以及各均值对应的有效样本数。
- 无法归属的模型/供应商计入「未知」桶，不从总览分母中排除；缓存命中、路由未完成等路径的归属需要在实施前逐一验证。

### 6.5 钻取请求日志

- 表格行和趋势区间可跳转到「API 请求日志」，通过稳定的路由查询参数携带时间范围、密钥 ID、供应商 ID、实际模型及可选 `status`；目标页初始控件必须反映参数，而不是仅把参数传给接口。
- 日志页补齐供应商和模型控件；清除过滤后重置分页。时间范围超出单条明细留存期时，仅钻取仍有明细的子区间并明确提示，或直接禁用并说明；不得把日汇总伪装为单条请求。
- `disable_logging` 的单条元数据只允许已定义的脱敏字段；详情抽屉和导出/复制路径也执行相同服务端白名单。

## 7. 数据定义与统计规则

### 7.1 数据集合与公式

- 基本单位为一条纳入监控的 `api_requests` 记录；`requestCount = COUNT(*)`、`successCount = COUNT(status = 'success')`、`failureCount = requestCount - successCount`、`successRate = successCount / requestCount`。无请求时成功率为 `null`，界面显示「—」。这不是上游尝试级分母。
- 同一请求若存在多条代理日志，首版**按记录计数**；交付前需核对重试、缓存命中、流式完成等路径，若多记则优先修正统一写入路径，再对齐首页与运维页，禁止只在一个页面去重。
- Tokens 展示输入、输出、缓存各自总和；总 Tokens 与首页必须走同一“缓存命中是否计费/计入”的现有口径，不能把 `cached_tokens` 直接叠加到生成的 `total_tokens`。相关卡片需写明是否包含缓存命中。
- `avgTffbMs = sum(valid tffb_ms) / validTffbCount`，有效性沿用并统一性能页现有 `tffb_ms >= 0` 规则；`avgResponseTimeMs` 仅用 `response_time > 0`；输出速度仅统计现有性能 SQL 认可的有效请求，并持久化**每条有效请求速度之和及其样本数**，不可通过汇总 Tokens ÷ 汇总耗时替代当前“逐请求速度的均值”。有效样本为 0 返回 `null`。
- 首页目前的 `avgResponseTime` 实际采用有效首字节耗时优先、否则回退响应时间的“有效时间”口径；新页面应独立标明 TFFB、端到端响应时间，不复用这个同名但不同定义的数值。若首页展示耗时，需同步澄清标签或统一定义。
- 供应商维度仅说明请求日志所归属的供应商，重试中间尝试的供应商未必有独立记录。不得把本表命名为“上游尝试成功率”或 SLA。

### 7.2 时间边界、精度与历史缺口

- `startTime = endTime - duration`，`duration` 分别为 24、168、720 小时；使用半开区间 `[startTime, endTime)` 和统一毫秒时间戳，前后端不要一个使用 `<=`、另一个使用 `<`。
- 日趋势按 `Asia/Shanghai` 划桶，但**总数仍是精确滚动窗口**，首尾日只统计窗口内部分。长周期可按日展示，不能因为可视化按天而放宽统计边界。
- 现有日汇总不具备首尾半天精度。推荐数据方案：保留至少 30 天可查询的小时级聚合以承载窗口内部整小时，同时让边界不足一小时的部分由尚存明细精确计算；为此明细实际留存必须覆盖 30 天前的边界（包括清理延迟和时区）。拟将默认明细留存提升到**至少 31 天**，并同步审查手工「清理旧日志」是否能绕过该保证。小时聚合是查询优化，不代替边界明细。
- 从上线时才开始积累新的小时级及完整性能日汇总；历史已删除的明细无法补出精确 `30d` 和过去的 TFFB/输出速度。迁移期首页与运维页同步显示可用覆盖范围；缺失项为 `null`/「—」，不得补零或把自然日近似值标为精确。能从仍存明细可靠回填的部分才回填，回填须幂等、可审计。
- 如果部署配置降低明细留存天数或手工清理使精确滚动无法保证：系统必须明确降级并展示覆盖范围，不能继续宣称精确。上线门槛是先使留存与查询一致。
- 旧版日汇总把网关缓存命中的请求 Tokens 计入总数，新版仅计非缓存命中；已清理明细无法还原差额。首页遇到带缓存命中的旧版汇总行时显示口径警告，不把历史数值冒充精确新口径。

### 7.3 日汇总与双读防重

- 扩展现有按日、密钥 × 供应商 × 模型的汇总，至少保存有效 TFFB 总和/样本数、有效响应时间总和/样本数、逐请求有效输出速度总和/样本数，以及支持「最近使用」的最大时间戳。已有请求数、成功数、Tokens 维度应复用，避免建两套相互矛盾的日表。
- 小时级聚合至少保存请求数、成功数、Tokens 与上述性能统计的总和/样本数，并建立时间及常用维度索引；只保留完成且可证明与明细边界不重叠的小时段。部分小时使用明细，不得重复累加。
- 清理时遵循“先汇总成功、再删明细”的事务/幂等原则；自动清理、手工清理及重试都不得双记。历史禁用日志密钥若有元数据，仅在符合新的隐私处理规则后纳入统计。
- 所有全局、密钥、模型、供应商查询应复用同一筛选和聚合口径；按维度求和必须等于总览（「未知」桶也计入），历史无性能数据时不应把有效样本数当作请求数。

## 8. 隐私、权限与留存

- 沿用现有 `fastify.authenticate` 管理路由和页面权限；实施前核对实际角色授权。新监控响应只含密钥 ID、名称与服务端计算的掩码，**绝不返回 `key_value`、请求/响应正文或自由文本错误内容**。
- `disable_logging` 配置文案调整为“禁用请求/响应正文记录；保留用于统计和排障的脱敏元数据”，并说明管理员可见范围。未获产品决策前不得把它悄悄扩展为记录正文。
- 禁用正文的密钥在服务端的列表、详情、搜索、导出（若有）统一走白名单：可见时间、ID、密钥 ID、模型、供应商、状态、Tokens、耗时、缓存命中等必要字段；不可见请求/响应正文、可能含敏感内容的 `error_message`、请求参数中的用户字段、IP、User-Agent 以及未经审计的 JSON 元数据。其他密钥原有日志能力不在本 PRD 中重新定义。
- 禁用正文时必须验证**写入侧**不会保存敏感文本，并在读出侧再次限制字段。已存的旧单条记录可能含敏感元数据：上线前设计清理或屏蔽策略，不因界面隐藏就认定安全。
- 删除密钥后，历史汇总中的密钥 ID 允许保留用于统计，但不应反查泄露原值；名称变更/删除时采用当前名称或「已删除密钥 + ID」，明确不是历史快照名称。权限与接口测试覆盖非管理员和直接调用 API 的情况。

## 9. 接口与性能要求（技术设计输入）

建议在现有 `/admin/config` 管理路由下增加按时间及维度过滤的运维聚合接口；可拆为总览、趋势和分页维度列表，但应共享服务端时间解析、数据集合、指标公式及隐私白名单。不要在前端读取整页日志后自行求和。

共同请求参数：`period`（`24h | 7d | 30d`）、可选 `virtualKeyId`、`model`、`providerId`、分页/排序字段；日志钻取使用与日志接口一致的精确 `startTime/endTime`。接口需验证时间范围、页大小、排序白名单及组合过滤，限制查询成本。

共同响应元信息：`startTime`、`endTime`、`timezone`、`updatedAt`、`dataCoverage`（明细/小时/日汇总各自覆盖区间、指标缺口与原因）、有效样本数。数值和 ID 用机器可读字段；显示文本和掩码由服务端安全提供。响应区分 `0`（确实为零）与 `null`（无数据或不可计算）。

数据量大时采用数据库聚合、分页、匹配过滤的索引和查询上限；上线前用接近生产量级的数据验证 30d 筛选及排序性能。刷新时使用同一个固定 `endTime` 返回相关视角，避免缓存过期、异步写缓冲或清理任务让页面卡片和图表短暂不一致；必要时暴露数据水位/刷新状态，不以伪造的实时性掩盖延迟。

## 10. 实施拆分与依赖

1. **统一口径与隐私**：盘点各协议请求日志的写入时点、重试记录、缓存命中和 `disable_logging` 路径；确定允许的元数据字段、首页指标口径，建立可复用的聚合计算与测试样例。
2. **持久化与留存**：扩展日性能汇总、建设小时聚合、事务性清理及必要索引；提升默认明细留存并约束手工清理；记录迁移与历史覆盖元数据。
3. **后端读取**：同一个时间窗口与过滤器供首页和运维页使用，支持总览、趋势、三种维度的服务端分页与排序；更新脱敏日志列表/详情读出。
4. **前端整合**：性能监测更名并升级，处理旧路由；新增四视角、筛选联动、数据缺口提示；日志页补齐模型/供应商过滤及 URL 参数回填；首页同步更改 7d/30d 时间定义和文案。
5. **验证与上线**：对齐历史与新增数据、清理前后、禁用日志密钥、删除密钥、跨时间/时区边界；先准备留存和汇总，再开放页面，避免一上线出现看似精确的 30d 错数。

## 11. 验收用例

| 编号 | 条件与操作 | 预期 |
| --- | --- | --- |
| AC-01 | 首页与运维页选择同一 `24h/7d/30d`，以相同 `endTime` 刷新 | 全局请求数、成功/失败数、成功率、Tokens 一致，时间起止和口径说明一致 |
| AC-02 | 30d 窗口落在两个非零点的自然日中间，期间有首尾边界外请求 | 边界外请求均不计入；日趋势首尾显示部分日，总和等于总览 |
| AC-03 | 某密钥请求分布于两个模型、两个供应商，含未知归属 | 模型、供应商拆分连同未知桶分别可与密钥/总览总数核对，不重复计数 |
| AC-04 | 仅有失败请求、零请求或无有效性能样本 | 成功率分别为 0%、「—」；性能无样本显示「—」，不显示 0 ms |
| AC-05 | 选择低成功率的模型和供应商并点击日志钻取 | 时间、模型、供应商、失败状态在日志控件和 API 查询中一致，可清除后重置分页 |
| AC-06 | 选择超过明细留存期的历史区间 | 仅展示可证明的汇总结果；单条钻取不可用或仅限实际明细子区间，并说明覆盖范围 |
| AC-07 | 密钥开启 `disable_logging`，发起含敏感正文、错误、IP 的请求 | 用量与允许的脱敏元数据可用；管理统计/日志列表/详情/API 响应中均无正文、敏感错误及 IP；写入侧遵守禁用正文约束 |
| AC-08 | 短密钥、重名密钥及已删除密钥进入榜单 | 短密钥全掩；同名由 ID 区分；历史归属保留，无接口返回完整密钥 |
| AC-09 | 执行定时或手工清理及重复重试 | 先汇总再删除，累计计数不重不漏；降低留存或旧数据不够时标出历史缺口 |
| AC-10 | 现有数据无历史 TFFB/速度字段 | 显示缺失及覆盖时间；不会用零、响应时间或简单平均替代 TFFB/输出速度 |
| AC-11 | 非授权用户直接请求新增接口或通过旧性能页面路由进入 | 权限与现有管理接口一致；旧书签不会出现另一套不一致的统计页 |

## 12. 待实施前验证的技术事实

这些是设计验证事项，不应被当作已实现的功能：

1. 各协议的失败、重试、流式中断、缓存命中是否恰好写一条符合本 PRD 分母定义的日志；`provider_id`/`model` 在早期返回时何时为空。
2. `disable_logging` 现有存量记录中的 `error_message`、`request_params_json`、`response_meta_json`、IP/User-Agent 具体可能包含什么；历史已清理/排除的区间是否可安全回填。
3. 提升明细默认留存至少 31 天的容量与性能成本，以及管理员可设置的留存值、手工清理入口、备份/迁移是否会破坏精确 30d 边界。
4. 旧首页 `all` 口径与新 `24h/7d/30d` 口径的共存：`all` 保持独立且不得标记精确滚动，历史日汇总仍可继续服务该入口。
5. 小时聚合与清理任务在中断、重复执行、异步日志写缓冲下的幂等及水位机制；不能因批处理间隙双算或漏算。

上述验证如发现既有日志不能满足单条请求口径，应先修正或在界面明确调整口径；不可为了通过验收而对单个页面单独打补丁。
